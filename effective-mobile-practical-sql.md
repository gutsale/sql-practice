# Effective Mobile Practical SQL Задачи
# Задача 1

Объяснить запрос

Есть 2 таблицы:

1) names:

| id | name         |
|----|--------------|
| 1  | John Doe     |
| 2  | Jane Doe     |
| 3  | Alice Jones  |
| 4  | Bobby Louis  |
| 5  | Lisa Romero  |

2) results:

| id | event            | winner_id |
|----|------------------|-----------|
| 1  | 100 meter dash   | 2         |
| 2  | 500 meter dash   | 3         |
| 3  | cross-country    | 2         |
| 4  | triathalon       | NULL      |

Что будет результатом следующего запроса

```sql
SELECT *
FROM names
WHERE id NOT IN (
    SELECT winner_id
    FROM results
);
```

## Разбор

Подзапрос:

```sql
SELECT winner_id
FROM results;
```

вернёт:

```text
2
3
2
NULL
```

Тогда условие превращается в:

```sql
WHERE id NOT IN (2, 3, NULL)
```

В SQL любое сравнение с `NULL` возвращает не `TRUE` и не `FALSE`, а `UNKNOWN`.

Поэтому выражение:

```sql
1 NOT IN (2, 3, NULL)
```

логически превращается в:

```sql
1 <> 2
AND 1 <> 3
AND 1 <> NULL
```

Последнее сравнение возвращает `UNKNOWN`.

Оператор `WHERE` возвращает только строки, где условие равно `TRUE`.

## Итог

Запрос не вернёт ни одной строки.

## Корректный вариант

```sql
SELECT *
FROM names n
WHERE NOT EXISTS (
    SELECT 1
    FROM results r
    WHERE r.winner_id = n.id
);
```
 Или если хотим оставить NOT IN:

```sql
 SELECT *
FROM names
WHERE id NOT IN (
    SELECT winner_id
    FROM results
    WHERE winner_id IS NOT NULL
);
```

# Задача 2

Напишите запрос SQL, используя Union All (не Union), который использует WHERE,, чтобы устранить дубликаты. Почему вам может это понадобиться?

## Решение

```sql
SELECT winner_id AS id
FROM results
WHERE winner_id IS NOT NULL

UNION ALL

SELECT id
FROM names
WHERE NOT EXISTS (
    SELECT 1
    FROM results
    WHERE results.winner_id = names.id
);
```

## Разбор

`UNION ALL` объединяет результаты запросов, но не удаляет дубликаты автоматически.

В первой части запроса выбираются все `winner_id` из таблицы `results`:

```sql
SELECT winner_id AS id
FROM results
WHERE winner_id IS NOT NULL
```

Во второй части через `NOT EXISTS` добавляются только те `id` из таблицы `names`, которых ещё нет среди победителей:

```sql
SELECT id
FROM names n
WHERE NOT EXISTS (
    SELECT 1
    FROM results r
    WHERE r.winner_id = n.id
);
```

Таким образом дубликаты устраняются вручную с помощью `WHERE NOT EXISTS`.

## Почему это может понадобиться

`UNION` автоматически удаляет дубликаты, но для этого выполняет для этого дополнительную сортировку, поэтому работает медленнее.

`UNION ALL` работает быстрее, потому что просто объединяет результаты без проверки повторов.

Если мы сами контролируем удаление дубликатов через `WHERE`, можно:
- повысить производительность;
- более гибко управлять логикой фильтрации;
- избежать лишней обработки данных.

# Задача 3

Написать SELECT запрос.

Напишите SQL-запрос, чтобы получить третью максимальную зарплату сотрудника из таблицы employees.

| worker_name | salary |
|---|---|
| A | 24000 |
| C | 34000 |
| D | 55000 |
| E | 75000 |
| F | 21000 |
| G | 40000 |
| H | 50000 |

## Решение

```sql
SELECT DISTINCT salary
FROM worker
ORDER BY salary DESC
LIMIT 1 OFFSET 2;
```

## Разбор

Сначала зарплаты сортируются по убыванию:

```text
75000
55000
50000
40000
34000
24000
21000
```

После сортировки:
- `OFFSET 2` пропускает первые две строки;
- `LIMIT 1` оставляет в результирующем наборе только одну следующую строку.

Таким образом получается третья максимальная зарплата.

## Почему используется DISTINCT

Если в таблице есть одинаковые зарплаты, без `DISTINCT` результат может быть некорректным.

Например:

```text
75000
55000
55000
50000
```

Без `DISTINCT` третьей строкой снова будет `55000`.

`DISTINCT` удаляет дубликаты зарплат перед сортировкой.

## Результат

```text
50000
```

# Задача 4

Удалить строки-дубликаты из таблицы.  
Нужно написать запрос на удаление (не select) дубликатов из таблицы:

| ID | Code | Number |
|---|---|---|
| 1 | A | 21 |
| 2 | B | 23 |
| 2 | B | 23 |
| 4 | D | 22 |
| 5 | E | 25 |
| 6 | G | 26 |
| 5 | E | 25 |

## Решение

```sql
WITH duplicates AS (
    SELECT
        *,
        ROW_NUMBER() OVER (
            PARTITION BY ID, Code, Number
            ORDER BY ID
        ) AS rn
    FROM table_name
)

DELETE
FROM duplicates
WHERE rn > 1;
```

## Разбор

### ROW_NUMBER()

Оконная функция `ROW_NUMBER()` нумерует строки внутри каждой группы:

```sql
ROW_NUMBER() OVER (...)
```

---

### PARTITION BY

```sql
PARTITION BY ID, Code, Number
```

разбивает строки на группы одинаковых значений.

Например:

| ID | Code | Number |
|---|---|---|
| 2 | B | 23 |
| 2 | B | 23 |

будут считаться одной группой.

---

### Нумерация строк

После применения `ROW_NUMBER()` строки получат номера:

| ID | Code | Number | rn |
|---|---|---|---|
| 2 | B | 23 | 1 |
| 2 | B | 23 | 2 |

---

### Удаление дублей

```sql
DELETE
FROM duplicates
WHERE rn > 1;
```

- строка с `rn = 1` остаётся;
- строки с `rn > 1` удаляются как дубликаты.

## Почему используется ORDER BY

```sql
ORDER BY ID
```

нужен для определения, какую строку считать первой внутри группы.

# Задача 5

К тебе обращается коллега за консультацией. У коллеги задача на написание SQL-запроса SELECT средней сложности (4-5 таблиц, подзапросы). Суть обращения: “Запрос выдаёт много лишних строк. Начинаю что-то менять – перестаёт что-либо выдавать вообще, пустой результат. Ну как же так? Можно ли как-то отлаживать SQL-запросы?”  
Какой совет дашь коллеге для решения подобных задач?

## Ответ

SQL отлаживается так же, как обычный код:
запрос разбивается на части, и каждая часть проверяется отдельно.

Если запрос возвращает слишком много строк, чаще всего проблема находится в `JOIN`:
- соединение сделано не по тому ключу;
- в условии `ON` не хватает части условия;
- связь между таблицами один-ко-многим размножает строки;
- используется `JOIN`, хотя по логике нужен `EXISTS` или предварительная агрегация.

Если запрос после изменений стал возвращать пустой результат, чаще всего проблема находится в фильтрации:
- слишком жёсткое условие в `WHERE`;
- несколько условий вместе отсекают все строки;
- подзапрос возвращает не те данные;
- используется `INNER JOIN`, который отбрасывает строки без совпадений;
- есть проблема с `NULL`, особенно в `NOT IN`.

---

## Как я бы предложил отлаживать запрос

### 1. Начать с основной таблицы

Сначала нужно выполнить самый простой запрос от главной таблицы:

```sql
SELECT *
FROM main_table;
```

Задача — убедиться, что исходные данные есть.

---

### 2. Добавлять JOIN по одному

Не нужно сразу соединять 4-5 таблиц. Лучше добавлять по одной таблице и после каждого шага проверять результат.
Если после добавления `JOIN` строк стало сильно больше, значит соединение размножает данные. Тогда нужно проверить ключи соединения и связь между таблицами.
JOIN сам по себе не “соединяет таблицы правильно”. Он просто выполняет правило, которое мы прописываем в ON.

---

### 3. Проверять условия `ON`

Важно отличать условия соединения от условий фильтрации.

Ошибка часто бывает здесь:

```sql
JOIN table2 t2
    ON m.id = t2.main_id
```

Если для правильного соединения нужно ещё одно поле, например дата, тип или статус, его тоже нужно добавить в `ON`.

---

### 4. Проверять `WHERE` по одному условию

Если результат стал пустым, нужно временно убрать все условия `WHERE` и добавлять их обратно по одному.
Так можно найти конкретное условие, после которого данные исчезают.

---

### 5. Запускать подзапросы отдельно

Если в запросе есть подзапрос, его нужно выполнить отдельно и посмотреть, что он реально возвращает.
Так можно понять:
- возвращает ли подзапрос строки;
- нет ли там лишних значений;
- нет ли `NULL`, который может сломать логику `NOT IN`.

---

### 6. Проверять промежуточные результаты

Во время отладки полезно временно выводить технические поля:

```sql
SELECT
    m.id,
    t2.id,
    t2.status
FROM main_table m
JOIN table2 t2
    ON m.id = t2.main_id;
```

Так легче увидеть, почему строки размножаются или почему совпадений нет.

---

### 7. Использовать LEFT JOIN для диагностики

Если `INNER JOIN` убирает слишком много строк, можно временно заменить его на `LEFT JOIN`, чтобы увидеть, где нет совпадений.

```sql
SELECT *
FROM main_table m
LEFT JOIN table2 t2
    ON m.id = t2.main_id
WHERE t2.id IS NULL;
```

Так можно найти строки из основной таблицы, для которых не нашлось пары во второй таблице.

## Главное правило

## Главное правило

Чтобы эффективно отлаживать SQL-запросы, недостаточно просто знать синтаксис SQL. Нужно понимать:
- как в целом работает SQL;
- в каком порядке СУБД выполняет запрос;
- как конкретная СУБД строит план выполнения запроса;
- как работают JOIN, фильтрация, группировка и индексы.
- использовать `EXPLAIN` и `EXPLAIN ANALYZE`
